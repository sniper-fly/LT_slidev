# slide-outline — スライド章立て設計スキル

## 目的

slidev 実装に入る前に、章立て (アウトライン) を確定させる。
**実装段階で見出しトーンや構成順序を直すと手戻りが大きい** ため、ここで以下を潰す:

- 見出し/コピー文のトーン (自己陶酔・演出過多)
- 1 スライド 1 メッセージへの整理
- 図 / 文章 / コードのどれで伝えるかの選択
- bio など時事性のあるコンテンツの鮮度
- アセット (画像・スクショ) の準備状況

## 全体フロー

```
Step 0: 素材把握 → Step 1: 全体構成 3 案提示 → Step 2: スライド単位の設計 → Step 3: OUTLINE.md 出力
```

## Step 0: 素材把握 (アウトライン作成前)

案出しに入る前に、ネタになる一次資料を読む。

- 元になる **Zenn 記事 / 技術ブログ** がある場合は全文を読む
- 実装本体 (リポジトリ) があれば README / CLAUDE.md / 設計文書を読む
- 既存スライドがある場合は構成・トーンを参考にする (ただし bio など時事ネタは流用しない、後述)

素材を把握した上で「最重要メッセージ」と「ストーリー軸」を 1〜2 文で言語化する。これが構成案の土台になる。

## Step 1: 全体構成 3 案の提示

スライド全体のストーリー軸について、**簡潔な 3 案をユーザーに提示する**。

- 1 案 = 各ページ 1〜2 行のサマリ × 想定枚数
- 軸の違い (機能訴求型 / 核心メッセージ型 / ストーリー駆動型 など) で 3 案にバリエーションを出す
- ユーザーが採用案を選ぶか、ハイブリッドや別軸の案を提示してくる前提で進める

主観の入る判断 (どの構成が刺さるか) はユーザーに委ねる。Claude は 1 案押し付けではなく **比較材料を揃える** のが役割。

## Step 2: スライド単位の設計

採用された構成案をベースに、各スライドを設計する。

### アウトラインのフォーマット

各スライドは以下 5 要素で記述する:

- **スライドタイトル**: 画面上部に出す一言キャッチ (8〜15 字目安)
- **メッセージ**: 聴衆に持ち帰ってほしい結論 (1 文)
- **内容**: 本文に出す要素 (箇条書き or 図解の中身)
- **口頭補足**: スライドには書かず話で添える情報
- **ビジュアル**: 図解・画像・コードの指示 (何を / どの形式で)

### 見出し・キャッチコピーの基準

タイトルとキャッチコピーは「役割を直球で示す機能的表現」を優先する。以下は避ける:

- **自己陶酔**: 発表者を主役化する文言
- **引き伸ばし演出**: ストーリーテラー風の一言で次への期待を煽る表現

#### 複数案 → ユーザー選択 の適用範囲

主観の入る見出しを 1 案で確定せず複数案を並べる、というルールは **以下のスコープに限定する**:

- LT 全体のメインタイトル
- キメスライド (中心メッセージ / クライマックス)
- 中心思想キャッチ (LT を象徴する一文)

各スライドの一言キャッチを毎回 3 案出すのは過剰。機能的タイトルで明らかに 1 案に決まるものは複数案不要。

(CLAUDE.md の「複数案比較」原則と一致)

### bio / 自己紹介の鮮度チェック

bio に書く「最近の趣味」「最近の作品」など時事系項目は、
過去スライドや別資料からコピペせず、毎回ユーザーに鮮度を確認する。

- 陳腐化するもの (旬の作品、最近やった/見た系) はそのまま流用しない

### 図 / 文章 / コードの選択

各スライドの「ビジュアル」を決めるとき、以下を問う:

- この情報は「図がパッと見で理解されやすい」か、「文章で書いた方が早い」か
- 図にした場合、本当に「センスのある図」を描けるか?
   描けないなら最初から文章版を採用する (実装後に差し替えるとコスト大)
- 図と文章を併載するなら、両方が独立に価値を持っているか (片方が冗長反復でないか)

#### 形式選択の判断ガイド

- **3 要素以下の関係**: 箇条書きで十分 (図にする価値が薄い)
- **時系列・因果**: Mermaid sequence で実装可能なら図、複雑すぎるなら文章
- **2 軸プロット / 位置取り** (トレードオフ図など): 図 (作図ツールで作成)
- **対比 (Before / After)**: 図 or 並列レイアウト (左右配置)
- **データ・統計**: 表 or グラフ
- **コードの差分・特定パターンを見せる**: コードブロック (文章化しない)

## Step 3: OUTLINE.md の出力

最終出力は `<slide-dir>/OUTLINE.md`。以下の推奨セクション構成で書く:

1. **最重要メッセージ**: 1〜2 文で LT のコアメッセージ
2. **ストーリー軸**: 章の流れを 1 行で
3. **スライド構造**: 各スライドの記述フォーマット (5 要素) の定義
4. **章立て**: 各スライドの詳細 (5 要素ベース)
5. **アセット準備状況**: 必要アセット一覧と入手状況 (後述)
6. **次フェーズへの申し送り**: Step 3-C 実装着手時の注意 (削った要素 / 統合判断 / キーメッセージ強調など)

### アセット準備状況テーブル

OUTLINE に必須セクションとして含める。

| # | スライド | 必要なアセット | 状況 |
|---|---|---|---|

**重要**: Claude が用意できないアセット (スクリーンショット / バズツイートのキャプチャ / 人物アバター / 外部の有償素材など) は **「未取得 (ユーザー側で用意必要)」と明示する**。

- ❌ NG: 「モックで代用可」「optional」「なくても OK」で誤魔化す
- ✅ OK: 「未取得。ユーザーが `slides/<topic>/assets/<file>.png` に配置する必要あり」と明示

Claude 自身が作れるもの (Mermaid 図 / Vue コンポーネント / `unplugin-icons` 経由のアイコン) は「Step 3-C で実装」と書く。両者を明確に区別する。

### 章番号を変更したときの参照リファクタリング

スライドの追加・削除・統合を行うと、本文中の「N 枚目で〜」「N 枚目に統合済み」のようなクロスリファレンスがズレる。

- 章番号を変えたら、OUTLINE.md 内の全番号参照を grep して更新する
- 番号参照は本文中だけでなく、アセット準備状況テーブル / 申し送り事項にも出てくるので漏らさない

### ユーザーが OUTLINE を直接編集する前提

ユーザーは OUTLINE.md を手で編集することがある。Claude が次に書き換えるとき:

- 必ず **Read で最新状態を取得してから** Write / Edit する
- system-reminder で「ファイルが変更された」と通知された場合は素直に追従する (勝手に元に戻さない)

## 補助観点: 伏線と回収 (LT らしさを上げたい場合)

LT は「タイトルの煽り → 結末で回収」「序盤の痛み → 終盤の解決で回収」のような仕掛けが効きやすい。アウトライン段階で伏線を張ったら、回収場所を決めておく。必須ではない。

## 完了基準

以下を満たすまで実装に進まない:

- [ ] 元になる素材 (記事・実装) を Step 0 で読み込んだ
- [ ] 全体構成 3 案をユーザーに提示し、採用案が決まった
- [ ] 各スライドが「1 スライド 1 メッセージ」になっている
- [ ] LT 全体のタイトル / キメスライド / 中心思想キャッチは複数案 → ユーザー選択済み
- [ ] bio など時事ネタはユーザーに鮮度を確認済み
- [ ] 各スライドのビジュアル選択 (図/文/コード) が決まっている
- [ ] 5 分 LT なら 8〜12 枚、それ以外は時間に応じた目安枚数に収まっている
- [ ] アセット準備状況テーブルが揃い、未取得は「未取得」と明示している
- [ ] 章番号を変更した場合、本文中の番号参照を全て更新済み
- [ ] アウトラインを `<slide-dir>/OUTLINE.md` に出力済み

## やってはいけないこと

- **素材を読まずに 3 案を作る**
   → 表層的な構成案になり議論が空転する
- **アウトライン段階で実装詳細 (CSS, レイアウト寸法) に踏み込む**
   → `slide-review` / 実装段階の責務
- **LT 全体のタイトル / キメスライドを 1 案だけ出して進める**
   → 複数案 → ユーザー判断
- **過去スライドの bio や雑談ネタを無検証で持ち込む**
- **「センスのない図」を描いて実装フェーズに送る**
   → アウトライン段階で「これは文章で良い」と判断する
- **Claude が用意できないアセットを「代用可」「optional」で誤魔化す**
   → 「未取得」と明示する
- **章番号を変更したのに、本文中の番号参照を更新し忘れる**
- **ユーザーが手で編集した OUTLINE を、Read せずに上書きする**
