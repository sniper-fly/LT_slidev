## Phase 3: Slidev スライド作成

### 3.1 根源的な目的

- **第一目的**: LT 会（5 分想定）で HeartGarden の価値を伝える。
- **聴衆**: 社内・社外双方を兼ねる「汎用 LT」想定。AI コーディング利用者およびセキュリティ関心層。
- **最重要メッセージ**: （Phase 2 記事執筆を経て確定するが、暫定）"AI コーディング時代にはサンドボックスが必要であり、それは実用的に組める"。
- **副次目的**: Slidev によるプログラマティックなスライド作成、および Playwright + LLM レビューループの PoC。

### 3.2 確定済み判断

| 項目 | 決定内容 |
|---|---|
| Slidev レビュー | **スクリーンショット連番 + 画像レビューエージェント** 方式 |
| 1 リポジトリ多スライド対応 | プラン段階では **調査タスクのみ記載**、実行段階で構成決定 |

### 3.3 作業ステップ

#### Step 3-A: 既存 LT_slidev 構成の調査

**目的**: `LT_slidev` の現状を理解し、1 リポジトリ多スライド管理への改修方針を決める。

- 調査項目
  - ディレクトリ構成、`package.json` の構成（pnpm-workspace の有無）
  - 現状のデプロイ方法（GitHub Pages)
  - 1 リポジトリ 1 スライドになっている技術的制約の特定
- 改修方針候補（実行段階で選択）
  - **案 1**: pnpm workspace で `slides/<topic>/` をパッケージ化
  - **案 2**: ルート単一プロジェクトで `slides/<topic>.md` を切り替え（Slidev のマルチプロジェクト機能調査）
  - **案 3**: ビルド時に slide 名を引数化、デプロイ先パスを `/<topic>/` で分岐
  - その他最適な案が見つかれば提案
- 出力: `docs/slidev-multi-slide-research.md`（実行段階で作成）
- 改修対象: スライド管理は `LT_slidev` に集約し、`HeartGarden` 側には持たせない

#### Step 3-B: スライド要素抽出

**目的**: Zenn 記事から 5 分 LT に収まる要素を選定する。

- 5 分 = 概ね 8〜12 枚を目安
- 選定基準
  - LT の最重要メッセージから逆算
  - 図解で伝わるもの優先（テキスト多めスライドは避ける）
  - 「もっと知りたい人は記事へ」の動線をエンディングに置く
- 完了基準
  - 想定聴衆に対して、前提説明 → 課題提示 → 解決策 → 効果 → まとめの流れが自然である
  - 各スライドの役割が明確で、1 スライド 1 メッセージを基本にしている
  - 5 分 LT に対して情報量が過多でなく、削る候補と残す理由が説明できる
  - 専門用語・背景知識の説明順序が破綻していない
  - 図解・コード・文章のどれで伝えるべきかがスライド単位で整理されている
- 最終出力の前に簡潔な3案をユーザーに提示。1ページあたり1~2行程度のサマリを3つ
- 最終出力: slidevディレクトリに章立て概要のマークダウンファイルを作成してユーザーに提案

#### Step 3-C: Slidev スライド実装

**目的**: スライド本文を作り込む前に、LT の内容に合う見た目・構成テンプレートを決める。

- 実装ベース
  - スライド管理は `LT_slidev` に集約する
  - `LT_slidev` 内で既存構成を拡張するか、マルチスライド向けの新しいディレクトリ構成にするかは Step 3-A の結論に従う
- 先に決めること
  - テーマカラー、フォント、余白、見出しスタイルなどの基本トーン
  - タイトル、章区切り、課題提示、図解、コード差分、まとめなどのページテンプレート
  - アーキテクチャ図、レイヤ別カード、コード差分表示など、HeartGarden の説明に必要な専用コンポーネント
- 進め方
  - Step 3-B で作成した章立て概要をもとに、内容に合いそうなテーマ・カラー・テンプレート案を複数作る
  - Slidev 公式テーマやインターネット上の既存リソースで適したものがあれば利用し、足りない部分は自作する
  - いくつかのサンプルページを作成して、ユーザーが方向性を確認できる状態にする
  - 採用するデザイン方針が決まったら、そのテンプレートに沿って各スライドの内容を肉付けし、最終的なスライドに仕上げる
- 出力
  - テーマ・カラー・テンプレート案を確認できる Slidev サンプルページ
  - 採用したテンプレートに基づく完成版スライド

#### Step 3-D: Playwright 自動レビューループ

**目的**: スライドのレイアウト崩れ・文字はみ出し・可読性を機械的にチェックする。
以下をSkillとして実装し、general-purpose agentから呼び出すようにする

- 実装手順
  1. Slidev を `slidev export` または dev server で起動 (まず起動チェックを行い、起動していなければユーザーに起動コマンドを提示して起動させる)
  2. Playwright で各スライドへ遷移し、PNG スクリーンショット連番取得
  3. 取得した画像群を画像理解可能な LLM（Claude / GPT-4o 等）にレビュー依頼
     - レビュー観点: 文字はみ出し、コントラスト、空白の偏り、図と文字の重なり、フォントサイズの一貫性、情報量、説明順序、スライド単位の主張の明確さ
  4. レビュー結果を JSON で受け取り、修正が必要なスライドを Markdown で報告
  5. ユーザーが修正方針を確認 → スライド修正 → ループ
- レビュー対象の完成基準
  - 1920x1080 表示で、すべての文字・図・コードが画面内に収まっている
  - 本文・注釈・コードの最小フォントサイズが可読範囲内である
  - 背景色と文字色のコントラストが十分である
  - 図・カード・コードブロック・見出しが重なっていない
  - スライドごとの情報量が過多でなく、発表者が説明しやすい密度である
  - タイトル、見出し、余白、フォントサイズ、色使いに一貫性がある
  - 1 スライド 1 メッセージを基本に、各スライドの主張が視覚的に伝わる
- レビュー判定レベル
  - `critical`: 文字はみ出し、要素重なり、読めないコントラストなど、必ず修正する問題
  - `warning`: 情報量過多、余白の偏り、サイズ不統一、説明順序の違和感など、修正推奨の問題
  - `note`: 好みや改善提案。必須修正ではないが、品質向上の参考にする
- JSON 出力スキーマ
  - レビュー LLM には、以下の JSON 形式で結果を返させる
  - `summary.hasCritical`: `critical` が 1 件以上あるか
  - `summary.criticalCount`: `critical` の件数
  - `summary.warningCount`: `warning` の件数
  - `summary.noteCount`: `note` の件数
  - `summary.overallComment`: 全体所見
  - `findings[].slideNumber`: 対象スライド番号
  - `findings[].severity`: `critical` / `warning` / `note`
  - `findings[].category`: `layout` / `readability` / `contrast` / `density` / `narrative` / `consistency` など
  - `findings[].issue`: 問題点の要約
  - `findings[].evidence`: スクリーンショット上でそう判断した根拠
  - `findings[].suggestedFix`: 修正案
  - `findings[].requiresHumanDecision`: 内容・構成・表現の好みに関わるため、ユーザー判断が必要か
  - 例:
    ```json
    {
      "summary": {
        "hasCritical": true,
        "criticalCount": 1,
        "warningCount": 2,
        "noteCount": 1,
        "overallComment": "大きな構成は自然だが、3枚目に文字のはみ出しがあるため修正が必要。"
      },
      "findings": [
        {
          "slideNumber": 3,
          "severity": "critical",
          "category": "layout",
          "issue": "右下の本文が画面外にはみ出している",
          "evidence": "スクリーンショット右下で文章の末尾が切れている",
          "suggestedFix": "本文量を減らすか、フォントサイズと余白を調整する",
          "requiresHumanDecision": false
        }
      ]
    }
    ```
- 実装上の論点
  - 画像レビューのモデル選定（コスト・精度のバランス）
  - スクリーンショット解像度（1920x1080 想定）
  - レビューループの停止条件（`critical` が 0 件、または反復上限 3 回）
  - `warning` と `note` は AI が修正案を出し、ユーザーが採用・保留・却下を判断できる形にする
- 出力: `tools/slide-review/`（または該当ディレクトリ）にスクリプト一式
